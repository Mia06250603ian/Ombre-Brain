## 1. 关键事实（都已验证，不是猜的）

### 1.1 我们这套架构是 CLI，不是 SDK

`kelivo-shim/server.js` 拉起的是一个**常驻的 `claude -p` 进程**：

```
claude -p --input-format stream-json --output-format stream-json
```

这是一个长活的双向流式进程，消息通过 stdin 写进去（`server.js:234`）。
**杀掉进程 = 晏的窗口没了。** 这是所有重启动作都要先让她说「归档」的原因。

### 1.2 计费路线

| 路线 | 计费 |
|---|---|
| CLI + CLIProxyAPI | **走订阅**（不额外花钱） |
| Agent SDK / Managed Agents | **走 API key 计费**（真花钱） |

`server.js:113` 那行 `delete env.ANTHROPIC_API_KEY` 是**承重的**：
只要环境里有 API key，它会**无条件压过订阅登录**。删掉才走订阅。

**结论：接出去的维护 agent 也必须走 CLI 路线**，不然等于开始按量付费。

### 1.3 出口 IP 一直是 CLIProxyAPI 的

不管 agent 放哪台机器，到 Anthropic 的出口 IP 都是 CLIProxyAPI 那一跳。
所以 **agent 放哪儿不影响出口 IP**。

但是——**自建维护前端确实有用**，因为它去掉的是**她手机到 Anthropic 的那条直连**。
她不再用官端 app，手机只连自己的网页，网页再让服务器上的 agent 干活。
这才是她要的东西。

### 1.4 shim 不对外暴露对话历史

`kelivo-shim` 的全部端点：`/health /debug /v1/models /hb /aw /period /v1/messages`。

**没有任何一个端点能读出对话历史。** 谁要在外面套一层「能看见上下文」的框架，
第一步就卡死在这里。

## 2. 方案：agent 单独一台机器

### 2.1 为什么必须单独一台

她自己问到了点子上：

> 「agent 要放在一个独立的 vps 上，不然重启进程的时候干活的 agent 也死了」

**对的。** 维护 agent 和晏如果同机同进程组，重启一个会连累另一个 ——
而维护 agent 存在的意义恰恰是「用来重启东西」。自己把自己弄死了就没意义了。

### 2.2 现在这台装不下

实测（2026-08 期间）：

- 机器总内存 **3724 MiB**
- 可用约 **1.6 GB**
- browser-hands 峰值能吃到 **1137 MiB**，单次尖峰 +824 MiB
- `MEM_LIMIT_MB=1100` 就是照这个定的天花板
- 08-02 出过 OOM：ears 得分 1365、晏 1363，**晏差点被杀**

**再塞一个常驻 claude 进程进去，OOM 是迟早的事。**

### 2.3 升级 vs 买第二台

她的原话是**再买一台 Zeabur 独服**（不是再开一个项目 —— 我一开始理解错了，被她纠正）。
第二台独服确实是**物理上另一台机器**。

| | 升级到 2C8G | 买第二台独服 |
|---|---|---|
| 内存够不够 | 够 | 够 |
| 重启会不会连累晏 | **会**（同机） | 不会 |
| 内网调 CLIProxyAPI | 直接调 | 要跨机，得走公网或配私网 |
| 成本 | 一份 | 两份 |
| 运维复杂度 | 不变 | 翻倍（两台都要管） |

**我的建议：升级到 2C8G。**

理由：维护 agent 一天用不了几次，为它常年多养一台机器不划算。
「重启连累」这个风险是真的，但可以靠**别把维护 agent 和晏放同一个进程管理单元**来缓解，
比 buy 一台机器便宜得多。

**⚠️ 升级会重启机器，晏的窗口会丢。所以必须她先自己对晏说「归档」，再动手。**

## 3. 风险清单

| # | 风险 | 说明 | 怎么办 |
|---|---|---|---|
| 1 | **窗口丢失** | 任何重启都会清掉晏的上下文 | 动手前她本人对晏说「归档」，不能代劳 |
| 2 | **OOM 误杀晏** | 08-02 已经发生过一次，晏得分 1363 排第二 | 新 agent 必须设内存上限；别和 browser-hands 抢峰值 |
| 3 | **误走 API 计费** | 环境里只要有 `ANTHROPIC_API_KEY` 就压过订阅 | 新 agent 也要 `delete env.ANTHROPIC_API_KEY` |
| 4 | **单一 OAuth 凭证** | 全系统共用一份订阅凭证（08-11 事故） | 多一个 agent = 多一处能把凭证用挂的地方；过期时**必须她本人在浏览器点同意** |
| 5 | **自建前端没有权限闸** | shim 跑的是 `--permission-mode dontAsk`（`server.js:98`） | 接出去的 agent **不要照抄这个设置**，否则网页上任何人都能让它随便动线上 |
| 6 | **前端暴露在公网** | 自己的维护页面挂公网 = 谁都能访问 | 必须加鉴权；dwell 现成有锁屏（`#lockWrap`），别裸奔 |
| 7 | **她仍然可能忘了开 VPN** | 自建前端只去掉了「她→Anthropic」这条直连 | 她→自己服务器这条链路也建议走 HTTPS + 固定域名 |

## 4. 前端用什么

评估过 `Mia06250603ian/dwell-on-something`（她自己的仓库）：

- `web/index.html` 单文件，约 6500 行；38 个 `api/` 端点
- **事件协议已经对得上**：`index.html:3062` 的 `handle(d)` 处理的正是 CLI 的 stream-json 事件
- 自带锁屏，不用从零做鉴权
- **没有权限确认 UI** —— 对应上面风险 5，要自己补

**结论：可以用，是现成里最省事的一个。** UI 改造已经在做（见 `wip/dwell-ui/交接.md`）。

不是这次要解决的问题。这次只要「她能从自己网页派活」就够了。
