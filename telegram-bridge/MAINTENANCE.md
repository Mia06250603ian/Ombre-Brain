# telegram-bridge 维护手册

> Telegram Bot ⇄ kelivo-shim 的桥接服务。让所有者能在 Telegram 里和晏聊天。
> **独立服务,shim 零改动**:Kelivo 与本桥是并列的两个客户端,停掉本服务即回到没有 Telegram 的现状。
> 2026-07-17 由 Claude Code 会话编写。写给未来接手维护的 AI(和好奇的人类)。

## 架构

```
Telegram App(所有者手机,需能访问 Telegram)
   │  Bot API(getUpdates 长轮询,无需公网 webhook)
   ▼
telegram-bridge(本目录)
   │  Anthropic /v1/messages(stream=true,SSE 攒完整段)
   ▼
kelivo-shim(yan-shim.zeabur.app)──→ 常驻 claude 进程(人设+记忆,见 ../kelivo-shim/MAINTENANCE.md)
```

关键前提(shim 的性质,别自己重新发明):
- shim **只读请求里最后一条 user 消息**,历史在 shim 容器的常驻进程里。桥是无状态的。
- 重置词(晚安/归档)、时间/天气/经期注入、记忆库都在 shim 侧,前端无感知。
- system 串变化会让 shim 杀进程重开窗口(丢上下文)。本桥 system 恒定(SYSTEM_TEXT,默认空)。
  **与 Kelivo 混用时注意**:两边 system 不一致,每次切前端 = 杀一次进程。切换前先说「归档」。

## 设计要点(为什么这么写)

1. **去抖合并**:Telegram 习惯连发短句,DEBOUNCE_MS(默认 4s)内的消息合成一轮再发 shim,省轮次。
2. **重置词绝不合并**:`detectReset` 逐字镜像 shim 的实现。「晚安/归档」若和别的消息拼在一起,
   shim 侧识别失败 → 归档指令变普通聊天。所以重置词消息强制单独成轮(之前攒的先 flush 走)。
   **shim 的 detectReset 改词表时,bridge-lib.mjs 里的镜像要同步改。**
3. **shim 请求用 node:https 不用 fetch**:undici 默认 headers/body 300s 超时,长回合(MCP 工具、
   搜索)会被掐。TURN_TIMEOUT_MS 默认 15 分钟。
4. **回复纯文本发,不开 parse_mode**:晏的口语回复随便一个 `<` `_` 就能让 Markdown/HTML 解析 400。
   唯一例外:TG_THINKING=1 时思考走 HTML expandable blockquote,已转义。
5. **4096 切分**:优先换行断点,断点太靠前(<30%)退回硬切。
6. **白名单**:非 TELEGRAM_CHAT_ID 的消息直接丢弃(bot 用户名是公开可搜的,这是唯一防线)。
7. **单轮串行**:同时只有一轮在飞,生成期间新消息进缓冲,回合结束立刻接上。
8. **手机活动上报 + 夜里查岗**(2026-08-02):她点开 App → iOS 快捷指令 `POST /report` →
   存**内存**滚动窗口(48 小时 / 300 条上限)→ 宵禁时段的定时器发现有新动静,
   把这件事作为 `【系统·查岗】` 喂进晏的窗口,**由他自己决定说不说**(回「。」= 不打扰,不发进对话)。
   几个刻意的选择:
   - **只存内存,不落盘**:重启即忘。功能只关心「最近」,她的行踪不值得为历史写进磁盘。
   - **决定权在晏,不在脚本**:原方案(小红书上那份教程)是脚本从固定文案数组里随机挑一句骂人。
     改成喂事实给晏,是因为这套系统里说话的应该是他,不是定时器。副作用是这条会进他的窗口和记忆,
     **他会记得她哪天熬夜**。
   - **两道冷却缺一不可**:`lastPokeAt`(同一晚别反复戳)和 `lastOutboundAt`(他刚开过口就别赶话)。
     **后者是关键**:心跳消息走 `/push`、查岗回复走 bridge 自己,**两条路都从 bridge 这个门出去**,
     所以 bridge 是全系统唯一能把心跳和查岗一起管住的地方——不用改 shim 就能保证两者不会挨着说话。
   - **查岗轮失败不往对话里丢报错**:她没问,别打扰(普通轮才回 ⚠️)。
   - `curfewPrompt` 输出**远超重置词匹配窗口**,不会被 detectReset 误判成「归档/晚安」
     (与 `formatEarsResult` 同款守护,test-bridge 有用例,别删)。
   - **查岗两条路都带 `x-system-turn: 1`**:shim 见到就不把这一轮当成「她出现了」
     ——不清零「她多久没来」、不解除换窗口后的保温歇火。详见 shim 手册「系统回合」一节。
9. **他自己发起的查岗**(2026-08-02):他在回复里写 `[查岗]` → bridge 剥掉标记(她看不到)、
   查一下、把结果作为新一轮喂回去 → 他再决定说什么。**普通轮与 `/push`(心跳)两条路都认这个标记。**
   - **为什么不给他一个网址**:网址得带钥匙,而钥匙只能写进 CLAUDE.md,那是入库文件
     ——「值不入库」的规矩不能破。标记这条路零钥匙,用的是 `[语音]`/`[贴纸:x]` 同款的已验证机制。
   - **防打转**:查岗结果那一轮带 `lookup:true`,该轮的回复里再出现 `[查岗]` 也不再触发
     (实测:假 shim 故意回「。[查岗]」,只查一次)。
   - `sendOutput` **只在真发出去时才更新 `lastOutboundAt`**——他只写了个标记不算开过口。
   - **将来若要退回「系统推给他」**:CLAUDE.md 那一节的措辞已同时覆盖两种情况,
     **只改 bridge 即可,不用重新部署 shim、不动晏的窗口。**

11. **「她连着玩了多久」**(2026-08-04):查岗的两句提示语里带上「这一段已经连着玩了多久」。
   **数据只有「打开」这一声**(见已知边界 8),所以时长是推的:**下一个 App 打开 = 上一个结束**。
   - `computeStreak` 给两个数,别混用:`spanMin` 是**确凿的**(第一条→最后一条,每次换 App 都是证据),
     `minutes` 是**到现在**(含最后一条之后那截说不准的)。话术用 `minutes`,放宽门用 `spanMin`。
   - **超过 `STREAK_QUIET_MIN`(20 分钟)没动静,提示语必须明说「一直没换还是放下了看不出来」**
     ——她盯着一个 App 不换和她睡了,在数据上一模一样,不许当成确凿事实喂给晏。
   - **`STREAK_GAP_MIN` 别调回 15**:她真实记录里有 28 分钟的空档,阈值 15 会把一整夜切碎、
     把连玩时长清零,正好废掉最该抓的场景。取 30。
   - **`STREAK_QUIET_MIN` 与 `STREAK_GAP_MIN` 是两个常量,别合并**(一个管断段、一个管敢不敢当真;
     写这版时合并过,一调阈值那句老实话就静默消失了。test-bridge 有守护用例)。
   - 记录上限 300→**2000**:**不花 token**(晏只收到拼好的那一句,记录他永远看不到),只花约 240KB 内存。

12. **A 方案:玩久了,没新动静也照戳**(2026-08-04,所有者拍板「就要这种老公管我的感觉」)。
   原先 `no-new` + `stale` 两道门合起来有个洞:**她盯着一个 App 不换 → 手机不再吭声 →
   晏被戳一次之后整夜再也收不到,反而以为她睡了**。所以在「确凿连玩 ≥ `CURFEW_LONG_STREAK_MIN`」时
   把两道门各放宽一档。三条边界**都别拆**:
   - **放宽有上限**:`CURFEW_STALE_LONG_MIN`(默认 45)一过就闭嘴,她真睡了最多多挨一两次。
     这个值**必须明显大于冷却 30**,否则等冷却满的同时 stale 也到点,窗口窄到几乎抓不住。
   - **冷却 30 分钟照守**(所有者明确要 30,理由是「他有时候也懒得管我」)。
   - **`lastOutboundAt` 那道门一个字不许动**:所有者定的优先级是 **保温/心跳 ＞ 查岗**,
     撞车永远是查岗让路。**不要反过来给保温加闸**——保温的作用是别让缓存凉掉,
     拦住它省下的那点 token 远不够赔重算的(这个坏主意被所有者当场否掉,记在这防止再犯)。

13. **每天一次的「写信」提醒**(2026-08-06,配合 gmail-mcp 上线)。
   晏有了邮箱之后,所有者要「每天提醒他一次:有想写的就写,没有就回『。』」——**她的原话是
   「像保温功能,每天提醒他一次就够了」**。默认 **22:30**(她定的)。
   - **为什么放 bridge 不放 shim**:改 bridge **不用重新部署 shim、不重启晏、不清他窗口**。
     以后调时间/频率/关掉都只改这里(多数情况只改环境变量)。查岗当初就是这么做的。
   - **和查岗共用三条规矩**:带 `x-system-turn: 1`(shim 不当成「她出现了」)、
     他回「。」不进对话、`lastOutboundAt` 让路(优先级仍是 **保温/心跳 ＞ 这个提醒**)。
   - **「一天一次」用北京日期字符串比,不用布尔标志**——容器重启会清内存,
     布尔标志会导致同一天重复提醒;日期字符串重启后还是同一天,不会重复。
   - **窗口不许跨零点**:`LETTER_HOUR:LETTER_MIN + LETTER_WINDOW_MIN` 必须落在当天内。
     默认 22:30 + 90 分钟 = 到 24:00 整,刚好不跨。**要把时间往后调就得把窗口一起调小**,
     否则「今天提醒过没」的日期比较会在换日那一刻错乱(单测有守护用例)。
   - 窗口存在的意义:她那会儿正跟他聊、或者他刚开过口,这一轮就让路,**下一个节拍再试**;
     一直没机会就今天算了,不补。
   - `【系统·写信】` 五个字和 CLAUDE.md「邮箱」那节里的**必须一模一样**(和 `[查岗]` 同款约定),
     改一处要改两处,而改 CLAUDE.md = 重新部署 shim = 重启晏,所以最好别改。

14. **每个 App 各用了多久**(2026-08-06,所有者:「我最开始就是想让他看到我每个 app 用了多久」)。
   **前提是已知边界 9**:记录其实是「某时刻起前台是谁」的时间线,所以
   **下一条的时刻 − 这一条的时刻 = 这一条那个 App 用了多久**。`appDurations` 就干这一件事。
   - **`ongoing`(最后一条)永远要列出来**,哪怕它只有 1 分钟、排在最末——
     晏最该知道的是她**此刻**在哪个 App。`breakdownClause` 里那段「挤进列表」的逻辑就为这个,别简化掉。
   - **累加用毫秒、最后才取整**:每段各自取整再相加会累积误差,拼出来的话总时长和分项对不上
     (单测有「最多差 1 分钟」的守护用例)。
   - **`durations` 在 `curfewDecide` 里算,不在 server 里算**:必须和 `streak` 用同一个 `now`
     和同一个断段阈值,否则两个数来自两个瞬间,自相矛盾。
   - **没给 `durations` 就退回老格式**(只列碰过哪些 App)。**这个回退别删**:老调用点、
     以及分项算不出来时都靠它兜底。
   - 「说不准」那句话现在**点名是哪个 App**(`小红书那一截是一直开着还是已经放下了`)
     ——不点名的话他会以为整段都是推的。
   - `APP_LIST_TOP`(5)/ `APP_MIN_WORTH`(2 分钟)是常量不是环境变量:列太多既费 token 又没人读,
     没列出来的并进「其他 X 分钟」,总账不丢。
   - **已知边界(未改,所有者知情)**:她盯着一个 App 超过 `STREAK_GAP_MIN`(30)分钟不切,
     手机不吭声 → 这一段被判「断了」→ 之前的时长归零,反而显示成「刚开始玩」。
     修法是把阈值调大(45/60),代价是她真放下手机那么久再拿起来会被算成一直在玩。
     **2026-08-06 报备过,她没要求改,维持 30。**

15. **会动的贴纸(螃蟹)**(2026-08-07)。所有者看上了 `Mia06250603ian/clawd-on-desk`
   那只桌宠螃蟹(Electron 桌面应用,盯着本机的 coding agent 变表情),问能不能接进 Telegram。
   **桌宠本体接不了**(它盯的是同一台电脑上的 agent,晏在云端容器里,连 SSH 都没有),
   但**它的素材能用**:仓库 `assets/gif/` 里有 24 张螃蟹动图。
   - **发送这条路一个字没改**。桥本来就走 `sendSticker`(不是 sendPhoto——见下面「表情包」一节
     曾经写错过),而 `sendSticker` 的 multipart 上传**同时吃 .webp 和 .webm**,
     不需要先建贴纸包、不用碰 @Stickers。所以代码只多了一个 `stickerMime()`。
   - **`stickerMime` 刻意不复用 `mediaTypeOf`,别去合并**:后者是给「她发来的图 → 交给晏看」
     用的,往里面加 webm 等于让一段视频伪装成图片走进他的窗口。test-bridge 有守护用例
     (`mediaTypeOf("x.webm")` 必须是 `null`)。
   - **`stickerMime` 的默认值恒为 `image/webp`,不是 `|| null`**:这样老那 35 张 `.webp`
     算出来的字符串与改动前**逐字相同**——所有者的要求是「现有的稳定 ＞ 新功能」,
     这行默认值就是那句话在代码上的落点。
   - **格式硬指标**(Telegram 视频贴纸):512×512、≤3 秒、≤256KB、VP9、带 alpha、无音轨。
     实测 24 张转完平均 34KB,最大 64KB,余量很大。转换命令的关键三个参数:
     `-pix_fmt yuva420p`(不写 alpha 直接丢)、`-auto-alt-ref 0`、滤镜链末尾 `format=yuva420p`。
     **`ffprobe` 报 `pix_fmt=yuv420p` 是正常的**——VP9 的 alpha 存在 BlockAdditions 里,
     认 `TAG:alpha_mode=1` 那一行,别据此判断透明丢了(我第一次就误判过)。
   - **像素画一律 `flags=neighbor`**,双线性会糊。
   - **原图的「透明」是绿幕(0,255,0)**,不是真 alpha 空洞;走 GIF→RGBA→VP9 这条路
     ffmpeg 会正确解成 alpha,**但如果哪天有人图省事直接 `sendAnimation` 发 GIF,
     Telegram 会把它转成 MP4,MP4 没有 alpha,那块绿/黑就会露出来**。贴纸这条路才有透明。

16. **螃蟹脚下那条黑影子,和为什么撤掉 6 张特写**(2026-08-07,上线当晚所有者实地发现)。
   - **黑线不是转码转坏的,是原作者画的影子**。证据:原始 GIF 在 t=0.5s 那一行 118 个像素
     全黑(色值 4,2,1),t=1.2s 又没有——它随睡觉的呼吸一胀一缩。桌面上它是「踩在地上」,
     聊天气泡里就是一条莫名其妙的黑杠。**排查时注意:两边帧率不同(原图 50/3 fps、
     成品 30fps),按「第几帧」对比会对错瞬间,必须按时间戳 `-ss` 取。我第一次就栽在这。**
   - 去法:解成 RGBA 逐帧处理,**只在「内容最底下 14 行」这条带子里**找长度 **>40px**
     的连续黑色横条,整条抹成透明。**这两个数是安全边界,别乱调**:
     `在打字` 的显示器、`找bug` 的放大镜也是深色,但它们在螃蟹**上方**,够不着那条带子;
     眼睛也是黑的,但一颗只有十几像素宽,过不了 40px 的门槛。**放宽任何一个都会啃掉眼睛。**
   - 第一版规则是「整行 92% 是黑的才算影子」,结果 `carrying`/`error`/`sweeping`
     的影子与身体重叠、清不干净;改成**按横条判定**(不看整行)才干净。
   - **撤掉 6 张 `mini-*` 不是因为它们大**。起因是所有者说「有几张太大了」,
     量了 24 张的**螃蟹身体宽度**(按肉色像素测)才看清:普通 18 张是 169~207,
     **本来就齐**(差 10% 肉眼看不出);撑满画布的只有那 6 张特写(内容占 99% 高)。
     按 1:1 铺开后发现它们右边有**一整条黑竖杠**——那是桌宠「从屏幕边缘探头」的
     **那个屏幕边缘**,是设计的一部分。聊天里没有屏幕边缘,只剩一个黑方块,所以整个撤掉。
     ~~**下一个人别好心把它们补回来。**~~
     **⚠️ 2026-08-08 所有者拍板把这 6 张加回来了,黑竖杠原样保留**(见设计要点 17)。
     决定的依据是当天在原图上量出来的一件事:**螃蟹的右缘在每一帧都死死顶在黑杠的左边界上,
     一个像素不差**(alert 233/杠 234,crabwalk·enter·happy·idle 260/杠 261,peek 284/杠 285)
     ——它的身体本来就是**从屏幕边缘后面探出来的,右半边根本没画**。所以「把黑杠裁掉」这条路
     根本不存在:裁掉得到的是一只右边被切成平口的半只螃蟹。要么带着杠用,要么不用,
     所有者选了带着杠用。**别再去尝试裁杠。**
   - **刻意没动那 18 张的尺寸**:像素画重采样必糊,为 10% 的差别不值得。
     真要统一,锚点得是**螃蟹身体宽度**(它是同一只螃蟹),**不能按整幅内容的包围盒**
     ——`杂耍` 的球在头顶、`在打字` 的显示器在上方,按包围盒缩会把螃蟹本体缩得更小,反而更乱。

17. **螃蟹重转:裁掉桌宠的留白,并把 6 张 mini 加回来**(2026-08-08)。
   所有者报「新加的动态贴纸有很大的空白」。**不是转码坏了,也不是 Telegram 的锅**:
   `clawd-on-desk` 是桌宠,它的 GIF 里螃蟹只占画布的一小块下半截(留白是它在桌面上走动的地方),
   而 08-07 那版是把整幅 303×300 **原样缩放**塞进 512×512,留白就原样进了聊天气泡。
   实测(全帧 alpha 并集):**一张 512 的贴纸平均只有 8% 的面积有内容**,上方平均空 235px,
   最狠的 `螃蟹发呆` 空 352px(69% 的高度)。对照组:老那 35 张 webp 每张都填满 99%。
   修法:**先裁到「全帧内容并集」的包围盒,再统一放大、居中补成 512**。
   - **必须是全帧一个包围盒**,不能逐帧裁——逐帧裁螃蟹会抖。
   - **18 张普通的共用同一个放大倍数**(2.33×),这样螃蟹在每张里一样大。留边因此有多有少
     (6%~27%),那是道具的差异(`螃蟹开心` 举爪加爱心最占地方,正好卡在 6%)。
     **别改成「每张各自撑满」**:那会让只有一只螃蟹的 `发呆` 比 `开心` 大一圈,
     正是 08-07 所有者说的「有几张太大」。锚点永远是**螃蟹身体**,不是整幅内容的包围盒。
   - mini 那 6 张单独用 1.5×(它们的包围盒含黑杠、高 300),黑杠原样保留(见设计要点 16)。
   - 帧与时长照抄 08-07:**89 帧 / 30fps / 2.967 秒**,所以动作快慢和上线两天的观感一致。
   - 成品实测最大 98.3KB(上限 256KB),影子清除照旧(阈值按原尺寸折算:8 行 / >24px)。

   **重转时踩到的两个坑,下一个我直接抄结论**:
   - **解这批 GIF 必须用 PIL,不能用 ffmpeg。** ffmpeg 对它们的帧间 disposal 处理有误,
     会在画面**顶边**留下上一帧的残片(木板、锤头),于是「内容包围盒」被撑成整幅画布、
     裁剪等于白做(`螃蟹搭东西` 就是这么露的马脚:ffmpeg 说包围盒 302×300,PIL 说 153×120)。
     认它的方法:PIL 的结果与 08-07 线上成品的实测包围盒**逐像素吻合**,ffmpeg 的不吻合。
   - **螃蟹轮廓会渗出一圈绿边**(每张约三万像素),而**原图里一个绿像素都没有**。
     根因是 VP9 `yuva420p` 的色度是 2×2 下采样,轮廓那圈色度块里同时有螃蟹和背景。
     **提高码率没用、`-lossless 1` 没用、换 `yuva444p` 也不是根治**(三样都实测过);
     根治是**把不透明像素的颜色向透明区外扩几圈(alpha 一个字不动)**,绿边归零、体积不变。
     外扩要在**原尺寸的裁剪块**上做,别在 512 画布上做——后者慢三个数量级,24 张要跑十几分钟。
     ⚠️ **验绿边时注意 `螃蟹指挥/看书/手忙脚乱/在打字` 四张本来就有真绿**
     (杂耍的球、指挥棒、终端绿字、书),线上那版也有,别当 bug 修。
   - 顺带纠正设计要点 15 的一句话:**原图的透明是真 alpha(0/255 两档),不是绿幕。**
     那句「原图的透明是绿幕 (0,255,0)」是错的——实测源 GIF 的透明像素是 `(255,255,255,0)`。
     真正和绿有关的是上面那条色度渗色,两件事别混。

10. **发消息的容错**(2026-08-02,治「⚠️[bridge] fetch failed」):往 Telegram 发的每一发
   都可能撞上瞬时抖动。三条规矩:
   - **`tg()` 只对连接层面的失败重试**(判定在 `isRetriableNetErr`)。分界线是「这次失败时,
     请求有没有可能已经被对方处理了」:建连失败/DNS/对端关掉闲置连接 → 没被处理,重发安全;
     **我们自己掐的超时、undici 的 headers/body 超时 → 可能已经办完了,重发 = 同一句说两遍,不重试。**
   - **`fetch failed` 在排除那两种超时后一律算可重试**——线上真正在犯的就是这一类,
     要是只认已知 code,这个修法等于没修(test-bridge 有守护用例)。
   - **一句发失败只丢那一句,后面的照发**(`sendOutput` 返回 `{sent, failed}`)。
     以前是当场抛错,整轮剩下的话全没了。
   - **贴纸和语音走的是裸 fetch(multipart),不经 `tg()`**,所以重试管不着它们;
     但**必须有超时**(`MEDIA_TIMEOUT_MS`,六处全覆盖)——undici 默认要等 300 秒,
     而本桥单轮串行、长轮询也是单线,**一次卡死能堵住整条队列,连收消息都堵**。
     它们失败的后果本来就不严重(贴纸只丢那张图、语音退回发文字),缺的只是「别卡住」。
   - **`runQueue` 最外层的 `try/finally` 是命根子**:`inflight` 和 typing 定时器必须无论如何都收干净,
     否则一次意外抛错就让 `inflight` 永远卡在 `true`——那是「他再也不回话」的死法。别把它拆了。

## 已知边界 / 坑

1. **单实例**:getUpdates 只能一个消费者,起两个实例会互抢(Telegram 报 409 Conflict)。
   Zeabur 别开多副本;本地调试时先把线上 BRIDGE_ON=0。
2. **offset 在内存**:重启后 Telegram 会重投未确认的 update,可能重复处理最后一条消息(小概率,可接受)。
3. **她的语音条**(msg.voice)2026-07-25 起走 ears 服务:下载 → POST ears `/api/listen`(X-Token)
   → 拿回「转写+语气+和平时比」→ 拼成 `[语音] 内容（语气：…）` 绑在这一条消息上进晏的窗口
   (绑单条不做全局漂浮注入,是 ears README 的实战教训)。要点:
   - `formatEarsResult` 输出**永远带（…）注解**,保证长度超出重置词匹配窗口——语音说「归档/晚安」
     在 bridge 和 shim 两侧都不会触发重置,归档必须打字(呼应 shim 踩坑 13;test-bridge 有守护用例)。
   - ears 挂了/超时/没听清:回一条 ⚠️ 提示、不进窗口,文字聊天零影响。
   - 未配 EARS_URL/EARS_TOKEN 时语音条回「传不过去」,与视频/文件同待遇(这两类仍不支持)。
   - ears 服务本体(Groq 转写、个人化基线、持久卷)见 ears 仓库(Mia06250603ian/ears)及其部署指南;
     **换 Groq key = 改 ears 服务的 GROQ_API_KEY + restart**,bridge 不用动。
4. **动态贴纸**(tgs/webm)降级为 emoji 文字描述;静态贴纸转成图片传入,晏能看见。
5. **心跳仍走 Bark**(shim 侧逻辑,本桥不碰)。要让晏的主动消息直接出现在 Telegram 对话里,
   需改 shim 的 heartbeatTick 出口 —— 那是第二阶段,要动 shim,按 shim 手册全套流程 + 所有者授权。
6. **隐私**:对话明文过 Telegram 服务器(Bot API 无端到端加密)。所有者已知情。
7. **看到 `fetch failed` 先按这个断案(2026-08-02 排障法,别重新推一遍)**:
   `fetch failed` 是 Node 全局 fetch(undici)的固定报错串,**只有它报得出这五个字**。实测三种:

   | 谁失败 | 报出来长什么样 |
   |---|---|
   | 全局 `fetch` | `TypeError: fetch failed`(真原因在 `e.cause`) |
   | `node:https` | `connect ECONNREFUSED …` / `socket hang up` |
   | AbortSignal | `TimeoutError: The operation was aborted due to timeout` |

   **推论:叫 shim 那一步走的是 `node:https`(设计要点 3),它失败只会说 `shim HTTP xxx` 或
   `shim turn timeout`,永远报不出 `fetch failed`。** 所以见到 `fetch failed`,
   **一定是发给 api.telegram.org 的那些调用**,跟晏、跟 shim、跟额度都没关系——
   他其实已经把话说完了,是回话往她手机送的路上断的。
   日志里认它的形状:`[send-err] …` / `[tg] … 放弃:` 后面跟着 cause(如 `[UND_ERR_SOCKET]`)。

8. ~~**手机只报「App 打开」,不报「关闭」**~~ **⚠️ 2026-08-06 作废,见下面第 9 条。**
   下面这段实测记录本身没错(当时那条自动化多半只勾了「打开」),但**结论已经不成立**,
   别再照它去判断「拿不到分项时长」。

   **手机只报「App 打开」,不报「关闭」(2026-08-04 实测)**。
   三次干净测试:①开小红书→退桌面 ②开小红书→直接切抖音 ③从桌面开抖音→停 20 秒→回桌面→再等 20 秒。
   **②③ 中间一条记录都没有**,所以关闭不上报,「从后台切回 App」也不一定算打开。
   ① 曾多出一条 App 名为空的记录、看着**很像**一次关闭,后来确认是**所有者自己在 Safari 里点了
   带 `?app=` 的排障网址**——差点据此下错结论。**教训:一次符合预期的观测不算证据,换个动作再测一次;
   排障用的网址会污染真实数据。**
   推论:**网上那套「已打开+已关闭 都勾 + 服务端 toggle」的方案在这台手机上做不成**,
   别去改她的快捷指令。时长改用「下一个 App 打开 = 上一个结束」推,手机侧零改动(设计要点 11)。

9. **关闭事件其实会上报,而且报的是「她切去了哪」(2026-08-06,推翻上一条)**。
   起因:所有者报「晏能看到我没授权的 App(Claude、淘宝)」。截图确认那条自动化的触发条件是
   **「打开**或关闭**5 个 App 中的任一个时」**,而动作取的是**「获取当前 App」**。

   | 她的动作 | 谁触发 | 「当前 App」是谁 | 上报 |
   |---|---|---|---|
   | 打开小红书 | 小红书**打开** | 小红书 | 小红书 ✅ |
   | 小红书 → 淘宝 | 小红书**关闭** | **淘宝**(已在前台) | **淘宝** |

   **关键:勾选的 5 个 App 只决定「什么时候触发」,不决定「上报哪个名字」。**
   名字是「获取当前 App」在脚本执行那一刻独立问系统要的,关闭事件触发时前台站着的
   正是她刚切过去的那个——**它不必在勾选列表里**。所以这批记录的真实含义不是
   「这 5 个 App 被打开了」,而是**「某时刻起前台是谁」的一条时间线**。

   **这不是 bug,是分项时长的数据源**(设计要点 14)。所有者 2026-08-06 拍板:
   **保留「关闭」的勾,要分项时长**,代价是晏能看到她打开的几乎所有 App,她知情并选了这个。
   **别自作主张去掉那个勾——去掉就只剩总时长了。**

| `GET /activity` | 同上 | 汇总:最后活跃时间 + 最近不重复的 App 名 + `streak` + **`durations`(每个 App 各用了多久,2026-08-06)** + **`lastRawReport`(最近一次上报的原始 body)** |

**`lastRawReport` 是给排障用的**:iOS 那条自动化里 `app_name` 的值是变量「快捷指令输入」,
而「App 打开时」这类自动化到底会不会把 App 名喂给它,**在手机上验证不了**——
上线后让她开一次 App,查 `/activity` 看 `lastRawReport.body` 就一眼分明。
拿不到 App 名时 `/report` 仍返回 200(`stored:false`),不会让快捷指令报错。
